Show the server code that made this possible 
// The intent is sequential. The runtime is not.
public async Task Transfer(int from, int to, decimal amt)
{
    var a = await db.Cards.FirstAsync(c => c.Id == from);
    var b = await db.Cards.FirstAsync(c => c.Id == to);

    if (a.Balance < amt) return Fail();   // ← stale read, both requests pass

    b.Balance += amt;   // credit
    a.Balance -= amt;   // debit

    await db.SaveChangesAsync();
    // UPDATE Cards SET Balance=@p WHERE Id=@id  ← last writer wins
}

The line to land with the room: neither of these was a clever attack. Both were the ordinary read → check → write pattern that every one of us has shipped, hit by more than one request at a time. Starbucks lost pocket change and some reputation. Flexcoin lost the company.
StrategyHow it worksCostReach for it when
Optimistic
byte[] RowVersion		 SQL Server bumps an 8-byte rowversion on every UPDATE. EF Core adds AND RowVersion = @original to the WHERE clause. 0 rows affected → DbUpdateConcurrencyException. Free until a collision happens Contention is rare. Human-paced edits, admin screens, ordinary CRUD — anything where a 409 is a fair answer.
Optimistic + retry Same, wrapped in a bounded loop that re-reads and re-validates before trying again. Jittered backoff. A few extra round trips under load The caller shouldn't see a 409 and the operation is safe to recompute from fresh state.
Pessimistic
WITH (UPDLOCK, ROWLOCK)		 Takes an Update lock at SELECT time inside an explicit transaction. The second request blocks rather than reading stale data. Serialises the row; throughput ceiling; deadlock risk Contention is high, or retrying is expensive/illegal — charging a card, moving money, allocating the last seat.
Atomic UPDATE
ExecuteUpdateAsync		 SET Balance = Balance - @x WHERE Id = @id AND Balance >= @x. One statement, so there is no window between read and write at all. Cheapest of all — one round trip The new value is a pure function of the old one. If this fits, use it.

Ask these three questions

  1. Can I express the whole thing as one UPDATE whose WHERE clause carries the business rule? → do that.
  2. If not: is a retry acceptable for this operation? → optimistic + RowVersion.
  3. If not: take the lock. → UPDLOCK in a short transaction, and measure the throughput cost.

Things that look like fixes and aren't

  1. BeginTransaction() with no lock hint. READ COMMITTED gives atomicity, not isolation. Both requests still read the old value. The most common false fix in code review.
  2. C# lock / SemaphoreSlim. Works on one process. Silently stops working the day you scale to two pods.
  3. Retrying without re-reading. Catching DbUpdateConcurrencyException and calling SaveChanges again rebuilds the original bug with extra steps.
  4. "It's never happened in prod." A lost update raises no exception and writes no log. Absence of alerts is not evidence of absence.
  5. Serializable everywhere. It does work, and it will flood you with deadlocks. Deliberate choice, not a default.
